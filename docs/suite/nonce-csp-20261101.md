# R1 Nonce-based content security policy - implementation review

## Scope

This covers Doc 16 SEC-022 and Doc 19 TEST-406. The policy allowed inline scripts (`script-src 'self' 'unsafe-inline'`), with a note to tighten it "until nonces land". It now runs only scripts that carry a fresh per-request nonce. There is no migration.

## Change

- **`src/middleware.ts`** creates a random nonce for every request and builds the policy with `script-src 'self' 'nonce-…' 'strict-dynamic'`.
  - The policy is sent with the request, which is how Next.js finds the nonce and adds it to its own scripts. It's also set on the response.
  - `'strict-dynamic'` lets those trusted scripts load the app's code chunks.
  - Refreshed sign-in cookies are still passed on together with the nonce headers.
- **`src/lib/security-headers.ts`:**
  - `createNonce()`.
  - The policy takes the nonce.
  - `'unsafe-eval'` is added only in local development, where React's tooling needs it.
  - Styles keep `'unsafe-inline'`, because the UI components set inline styles.
  - Everything else is unchanged: only this app and its own Supabase project, no frames, no objects, `base-uri` and `form-action` limited to the app.
- **`next.config.ts`** now sends only the Permissions-Policy. Two content security policies would both be enforced.
- **`src/app/layout.tsx`** is `force-dynamic`, so every page renders per request with that request's nonce. A page built ahead of time would have scripts without one, and they would be blocked.

## For the reviewer

1. **Every page now renders on request** (67 routes, none static). Most pages were already dynamic because they sit behind sign-in. The cost is a little server time on the few public pages.
2. **Styles still allow inline content.** Removing that needs the UI components to stop using inline styles; that's not planned for R1.

## Verification

- **Jest, `security-headers.test.ts`, 8 cases:**
  - Script rules require the nonce, with no `unsafe-inline` for scripts and no eval in production.
  - The allowed hosts and Permissions-Policy are unchanged.
  - Nonces are unique.
  - The middleware sends a fresh nonce on each response and forwards the same policy for Next.js.
  - Refreshed sign-in cookies still reach the page and the browser.
- **Production build:** it compiles, with all routes dynamic.
- **Running the built app:**
  - The sign-in page's response has the policy, and all 35 of its script tags carry exactly that nonce, with none missing.
  - Two requests get different nonces.
